# AGENTS.md

Instructions for AI coding agents working in this repository. This file is the single
source of agent instructions: the short overview and hard rules, the architecture and
collection-cycle notes folded in below, and links out to https://klag.dev for the long
reference tables (every environment variable, every metric). Read this file before
changing code.

## What this is

**Klag** — a Kafka consumer lag exporter. Java 21 on Vert.x 4.5.34, Micrometer for metrics,
Apache-2.0. It polls Kafka's AdminClient read-only and exports lag and derived signals to
Prometheus, Datadog, or OTLP. Docs: https://klag.dev (machine-readable at
https://klag.dev/llms.txt).

Are you trying to *use* Klag rather than develop it — install it, connect it, read its
metrics? Then you want the skill, not this repo: `/plugin marketplace add themoah/klag`,
or fetch https://klag.dev/.well-known/agent-skills/index.json. There is also a read-only
documentation MCP server at `https://klag.dev/mcp`.

## Build and test

Java 21 required (`sdk use java 21.0.9-tem`). Use `./gradlew` locally; CI calls `gradle`
directly, as no wrapper JAR is committed.

```bash
./gradlew compileJava
./gradlew test
./gradlew assemble              # fat JAR
./gradlew run                  # run with hot-reload
./scripts/test-helm-chart.sh    # chart templating, offline
./scripts/check-plugin.sh       # plugin manifest shape
cd website && npm run build && npm test   # docs site + generators
```

`./scripts/e2e-test.sh` and `./scripts/e2e-strimzi-test.sh` spin up real clusters — slow,
and they need Docker. Do not run them speculatively.

**GraalVM native image (optional).** Build with a GraalVM JDK 21 (`native-image`) via
`gradle nativeCompile` → `build/native/nativeCompile/klag`; `docker build -f Dockerfile.native`
produces the distroless runtime image. Reflection metadata comes from the GraalVM Reachability
Metadata Repository (auto-enabled); the entry point is `KlagLauncher`. Native config lives in the
`graalvmNative` block of `build.gradle.kts`. Details:
[https://klag.dev/deployment/native-image](https://klag.dev/deployment/native-image).

## Invariants — do not break these

1. **Admin request volume must stay independent of topic count.** Each collection cycle
   fetches committed offsets per group, then makes *one* batched `getLogEndOffsets(Set)`
   call for the union of their topics. Reintroducing a per-topic fetch turns one call into
   four requests × every topic × every cycle. `MetricsCollectorBatchingTest` pins this.
2. **Deleted topics are filtered before `describeTopics`.** One unknown topic fails the whole
   batch, and committed offsets outlive a deleted topic for `offsets.retention.minutes`. A
   failed `listTopics` must propagate, never fall through unfiltered.
3. **Partial cycles hold the failed groups' series and clean up the rest.** Cleaning against
   the cycle's incomplete key set alone would delete live series, so the failed groups'
   previous keys are added back first. The MCP snapshot still publishes, but an *empty*
   snapshot is never published.
4. **Adding a metric means updating `dashboard/demo-dashboard.json`** and the metrics tables
   in this file ("Metrics exposed" below) and `website/src/content/docs/metrics/`.
5. **Version bumps.** One bump of `version` in `build.gradle.kts` per PR that changes the
   application, and `charts/klag/Chart.yaml` `appVersion` plus the artifacthub annotation
   must match it. Website-only or docs-only changes do not bump.

## Style

Async operations return `Future<T>`. Java 21 records for DTOs. SLF4J + Logback. Config
resolves classpath `application.properties` → external `KLAG_CONFIG_FILE` → `KAFKA_*` env
vars, and every `Env`-backed variable also resolves from `-DNAME` and `-Dname.dotted`.
Match the surrounding code's comment density and naming rather than importing a new style.
Bump the version in `build.gradle.kts` after each minor or major application change.

## Architecture at a glance

```
src/main/java/io/github/themoah/klag/
├── MainVerticle.java          # entry point, HTTP router, lifecycle
├── config/AppConfig.java      # HTTP_PORT, KAFKA_HEALTH_CHECK_INTERVAL_MS
├── health/                    # KafkaHealthMonitor, HealthCheckHandler, HealthStatus, VersionHandler
├── kafka/                     # KafkaClientService[Impl], KafkaClientConfig, KafkaClusters, KafkaClusterSpec
├── metrics/                   # MetricsCollector, MicrometerReporter, PrometheusHandler
│   ├── velocity/              # LagVelocityTracker, TopicLagHistory
│   ├── hotpartition/          # HotPartitionDetector, HotPartitionConfig, StatisticalUtils
│   ├── dataskew/              # DataSkewDetector, DataSkewConfig
│   └── timelag/               # TimeLagEstimator, TimeLagConfig, OffsetTimestampTracker, PartitionOffsetHistory
└── model/                     # records: ConsumerGroupLag, ConsumerGroupState, PartitionOffsets, LagVelocity, ...
```

Vert.x reactive framework, `Future<T>`-based async API. The collection cycle runs in two
phases — committed offsets for every group (in waves of `KAFKA_MAX_CONCURRENT_GROUPS`), then
**one** batched `getLogEndOffsets(Set<String>)` for the union of their topics (one
`describeTopics` plus three `listOffsets` for the whole set, not per topic; with
`KAFKA_CHUNK_COUNT > 1` the union is split into that many batches, so it is one such batched
call *per chunk*, still not per topic). Lag assembly after that is pure computation.

**Deleted topics are filtered before `describeTopics`.** The Vert.x wrapper resolves
`describeTopics` via `allTopicNames()`, so one unknown topic fails the whole batch — and
committed offsets outlive a deleted topic until `offsets.retention.minutes` (7d), which would
keep every cycle partial and stale-gauge cleanup frozen that long. The union is intersected
with one cached `listTopics()` per cycle; absent topics are treated as deleted (series retired
in 1–2 cycles). Cost: asymmetric ACLs (offsets readable, topic not) look like deletion.

**Partial cycles skip cleanup but still publish the MCP snapshot.** A permanently failing
group (ACL gap, wedged coordinator) freezes stale-gauge cleanup indefinitely — deliberate,
documented in troubleshooting, fixed by ACL or `METRICS_GROUP_EXCLUDE`. The snapshot is
exempt so agents don't read hours-old data while `/metrics` stays current; an *empty*
snapshot is not published, since wiping the agent view is worse than a stale one.

## HTTP endpoints

| Endpoint | Purpose |
|----------|---------|
| `/healthz` | Liveness probe (always 200) |
| `/readyz` | Readiness probe (200 if any configured Kafka cluster is UP, 503 if all are DOWN) |
| `/metrics` | Prometheus scrape endpoint (if enabled) |
| `/version` | Build information |
| `/mcp` | MCP endpoint for AI agents (JSON-RPC over POST; if `MCP_ENABLED=true`) |

## Configuration reference

Every `Env`-backed variable resolves in order (first non-blank wins): env var `NAME` → JVM
property `-DNAME` → dotted `-Dname.dotted`. Config precedence: classpath
`application.properties` < external file at `KLAG_CONFIG_FILE` < `KAFKA_*` env vars. Any
`KAFKA_X_Y_Z` env var maps to `kafka.x.y.z` and is forwarded to the AdminClient.

The full environment-variable tables (app, Kafka, metrics, hot-partition, time-lag, commit
freshness, ISR, data skew, MCP, logging, and OTLP) are reference material, so they live at
[https://klag.dev/configuration/reference](https://klag.dev/configuration/reference) rather
than being duplicated here. Keep that page in sync with the code; when you add or change an
env var, update both the reporter/collector + its tests and the reference page.

## Metrics exposed

The complete metric catalogue with per-metric tag notes is reference material: see
[https://klag.dev/metrics/overview](https://klag.dev/metrics/overview) and the page per
metric under `website/src/content/docs/metrics/`. The short list: `klag.consumer.lag`
(+ `.sum/.max/.min` aggregates), `klag.partition.log_end_offset` / `log_start_offset`,
`klag.consumer.committed_offset`, `klag.consumer.group.state`, `klag.topic.partitions`,
`klag.consumer.lag.velocity`, and the conditional families (hot-partition, time-based lag,
data-loss-prevention, commit freshness, ISR, data skew). **When adding a new metric, always
also update the Grafana dashboard (`dashboard/demo-dashboard.json`).**
